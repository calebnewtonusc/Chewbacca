# Developing expertise across domains

Use this protocol when learning a new domain or improving how the agent learns.
It is a proposed operating method. Its effectiveness requires comparative tests.
The [decision standards](../../../docs/DECISION-STANDARDS.md) apply throughout:
mathematical evidence, creative alternatives and authorized private accumulation.
The current registry and runtime are generic infrastructure. An outcome advantage
remains a hypothesis until comparative and later-session tests demonstrate it.

## Define the competence before collecting material

Choose observable tasks, their outcomes, failure severity, permitted interventions,
cost units and environment. Separate knowing a rule, applying it in a familiar
case, recovering from failure, and transferring it to an unfamiliar case. A source
inventory is not a competence inventory.

Build a task graph for independent research, implementation and verification.
Build a knowledge graph only where multi-hop questions justify it over a table.
Keep source assertions, inferred rules and observed outcomes distinct. Record
contradictions, dates and identity uncertainty rather than merging them away.

## Select learning experiments

Start with a frozen baseline and a concrete failed or uncertain task. List competing
causes such as missing knowledge, bad retrieval, ambiguous identity, planning error,
tool misuse, stale state or a wrong objective. Choose a test that distinguishes them.
Do not repair a retrieval failure by adding more prose to an already unread skill.

Rank proposed experiments by expected reduction in consequential error per unit of
time and cost. When probabilities are unknown, state ordinal priorities and test
sensitivity; do not invent numerical information gain. Preserve user-requested
reading scope even when a particular experiment has enough evidence to proceed.

For each lesson, record source and inspected scope, the observed failure, the
general principle, boundary conditions, the concrete procedure change and a
counterexample. Keep application-specific selectors, schemas and pricing in the
domain skill. Keep reusable principles here only when their scope is justified.

## Test learning separately from performance

1. Run the corrected development case to check the proposed mechanism.
2. Run untouched tasks from the same domain and the existing regression set.
3. Run a separately prepared task in another environment or domain to test transfer.
4. Recheck after a later session to test persistence and successful retrieval.
   Record the lesson version actually retrieved, the action it changed and the
   independently checked outcome. Compare against the earlier failure; merely
   finding the lesson in storage does not pass this test.

Use a verifier separate from the generator, anchored to actual output. Freeze task
selection and judging criteria before candidate results. Report every assigned
task, including safe stops, crashes and interventions. Group near-duplicate tasks
when estimating uncertainty. Repeated tuning on a holdout turns it into training
data; replace it before the next confirmatory test.

Compare equal-budget alternatives: the unchanged agent, a simpler checklist or
retrieval method, and the candidate procedure. Ablate the supposed learning
mechanism. Extra context, tools or spending can explain a gain without improved
learning. Report what changed instead of attributing every improvement to expertise.

Keep authorized private records of task identity, observed state, decision, action,
outcome, correction and source provenance. Minimize personal data and exclude
credentials. Record rights and publication scope before promoting a private example
into a shared procedure. Synthetic fixtures are shareable only when they disclose
no client facts; they do not establish live performance. A Jev recommendation is
an input to evaluation, never an independent outcome witness or permission grant.

## Promotion and rollback

Require both relative improvement and a predeclared absolute success floor, with
separate severe-error and cost limits. Statistical significance alone can accept
an unusable system. `gtme-learning evaluate` is a domain-independent local paired
test despite its historical name; its declarations and hashes do not prove sealed
tasks, independent evaluation, or authentic external observations.

Promote only the scope supported by results. A Clay improvement does not establish
spreadsheet or CRM competence. Save the old procedure, candidate, test identities,
evidence and limits. On regression, restore the last verified version and preserve
the failure as a test. Never weaken a fixed success criterion to make a candidate
pass. Record untested transfer as a hypothesis.

Training observation, 2026-09-23: independent review found that six improvements
in one hundred tasks could pass a relative sign test while ninety-four tasks still
failed. This motivated separating experimental improvement from operational readiness.
